# Project 24: Manual Chaos Test

## Objective
Record recovery from failure: deliberately **stop a running service**, observe the outage with a health monitor, **restart it and verify recovery**, and write up the event as **incident notes** with a real timeline and recovery metrics (MTTD / MTTR).

## Setup
- Workstation: the Ubuntu 24.04 Linux VM used for previous projects (Terraform + AWS CLI)
- Service under test: Apache `httpd` on 1 x Amazon Linux 2023 `t3.micro`, `/health` endpoint returns `OK`
- Fault injection and restart: AWS Systems Manager Run Command (no SSH, no port 22)
- Monitor: `scripts/monitor.sh` on the VM polls `http://<public-ip>/health` every second
- Self-healing: systemd drop-in `Restart=on-failure`, `RestartSec=5` (crashes auto-restart, a clean stop does not)
- Region: ap-south-1 (Mumbai)

## Chaos scenarios
| Scenario | Fault injected | Recovery | Hypothesis |
| --- | --- | --- | --- |
| `stop` (main task) | `systemctl stop httpd` | **Manual** `systemctl start httpd` after collecting evidence | Monitor detects the outage within seconds; service is healthy again within seconds of the restart; nothing restarts it on its own |
| `kill` (optional) | `systemctl kill -s SIGKILL httpd` (simulated crash / OOM kill) | **Automatic** - systemd `Restart=on-failure` | Outage is limited to ~`RestartSec` + start-up time with no human action |

The `stop` vs `kill` comparison shows why a clean stop needs a human (or automation) while a crash can self-heal.

## Test flow (`scripts/chaos-test.sh`)
```
1. Pre-flight     SSM agent Online, /health = 200 (abort if already broken)
2. Steady state   record systemd state, start monitor, 10 s of healthy baseline
3. Inject         stop (or SIGKILL) httpd via SSM, timestamp taken on the instance
4. Detect         wait for the first failed health check  -> MTTD
5. Restore        stop: collect evidence (status, journal, port 80), hold the outage
                        for <outage-seconds>, then systemctl start httpd via SSM
                  kill: no action, wait for systemd auto-restart
6. Verify         first good check -> MTTR; 15 s stability window with 0 failures;
                  systemctl is-active = active; app page loads from the VM
7. Report         metrics + PASS/FAIL, generate incident notes
```
If the script is interrupted while the service is down, it prints the SSM command to restore it.

### 3. Confirm steady state
Wait 2-3 minutes for the bootstrap to finish, then:

## Troubleshooting
- `ABORT: instance is not Online in SSM`: wait 2-3 minutes after apply; the instance needs outbound internet and `AmazonSSMManagedInstanceCore`.
- `ABORT: service is not healthy`: bootstrap still running (check `/var/log/cloud-init-output.log` via SSM) or `allowed_http_cidr` does not include your VM's public IP.
- Negative or odd MTTD values: the VM clock is not synchronised; check `timedatectl`.
- Test interrupted while the service is down: run the restore command the script prints, or `aws ssm start-session --target <instance-id>` then `sudo systemctl start httpd`.
- `kill` scenario never recovers: systemd gave up after `StartLimitBurst` (5 restarts in 300 s); run `sudo systemctl reset-failed httpd && sudo systemctl start httpd`.
- `base64: invalid option -- 'w'` / `date` errors: run the scripts on Linux (GNU coreutils), not macOS.

## Verification
- `systemctl stop httpd` causes an immediate, detected outage (HTTP 000 - connection refused) that does not self-heal.
- `systemctl start httpd` restores the service; the monitor returns to HTTP 200 and stays UP for the stability window.
- MTTD, MTTR and downtime are measured from timestamps, not estimated.
- Optional: a SIGKILL crash is recovered automatically by systemd.
